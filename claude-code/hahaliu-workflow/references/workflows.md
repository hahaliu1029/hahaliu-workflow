# 端到端 Playbook

选路(fast/focused/full/review)见 SKILL.md;本文件是选定任务类型后的完整走法。所有 playbook 共享: 默认不 commit(任何 git 写仅在用户本次明确授权后)、修改类任务过文末的 Task Delta Adapter、完成前按分级验证、子代理派发按 [agents.md](agents.md)。

## A. 新功能(无项目 auto-skill 覆盖)

1. 侦察: 并行只读子代理扫结构/契约面/测试缝隙(低档模型)。
2. 澄清门禁: 先过 routing.md「用户目标定位」——还在验证「值不值得做」的走 office-hours(替代 grill,不连跑),已决定做才进成熟度四档(四档与 grill 变体选择见 routing.md): 已明确→跳过澄清并说明;只剩 2-3 清晰方案→brainstorming 取批准;一句话需求→MP grill 系逐项展开决策树(可查的事实不问用户,按 routing.md「定向调研」在事实缺口处按需查,不预跑全面研究),以共同理解回执收口并获用户明确确认(短确认即可)才继续;巨大看不清路线→wayfinder。四档选一,不叠加。
3. 计划: 走过 grill 的需求先过 routing.md「第二次门禁」(规模×副作用授权)再定出口——只要讨论结果就对话输出即止;单会话小需求转 focused 直接做,不强上 spec/tickets;多会话/需持久工件才 MP to-spec(用户确认测试 seam)→to-tickets(tracer-bullet 垂直切片,Blocked by 声明依赖)→过文末「Spec 收敛门禁」实施前检查,且 grill→spec→tickets 保持同一上下文,换会话用 handoff 桥接。未走 grill 的常规计划用 writing-plans(bite-sized 任务+验证点)。访谈中定不了、必须跑起来才知道的问题→handoff→prototype→handoff 回来再继续 grill。to-spec 只综合不访谈,访谈欠账没人补。
4. 跨层功能先冻结共享契约(schema/API 形状/类型),这部分串行自己做。
5. 实现: 契约冻结后按票推进,默认用 **uncommitted ticket executor** 逐票执行。不整套调用 MP implement(完成协议含 commit)或 superpowers subagent-driven-development(依赖 worktree/commit/按 commit 打 review 包)——两者都以 git 写为完成协议,超出默认授权;仅当用户本次明确授权 worktree+commit 时才用它们。
   Executor 每票八步(票少→主上下文顺序做;票多且独立→每票 fresh subagent,派发词逐字带 git 授权边界):
   1) 取 frontier ticket(所有 blocker 已完成的票);
   2) 任务前快照(Task Delta Adapter 第 1-2 步,基线以**本票开始时刻**为准);
   3) 按票 TDD 实现(先 RED 后 GREEN);
   4) 按 Task Delta Adapter 第 3 步算**本票专属 patch**;
   5) 把 patch 显式交给 Standards+Spec 双轴 review(上下文隔离,结论并列);
   6) 跑该票定向验证命令,用当次输出说话;
   7) 更新本地 ticket 状态与进度(仅限已授权的本地工件);
   8) 不 commit——累计 delta 留给用户处置,完成报告明确声明未提交。
6. 评审: 按有无 spec 选单轴/双轴;新输入面/鉴权面加 security 镜头;高风险加 codex challenge。
7. 验证+报告: 按分级跑;报告固定五项——结果 / 改动文件 / 验证命令与输出 / 未验证项与风险 / 未提交声明;启用收敛门禁的任务附验收标准重放记录。

### Spec 收敛门禁(仅多会话/大型/高风险的 full 任务)

普通单会话 full 不启用,避免规格工程化;走 to-spec→to-tickets 的任务两段都过:

**实施前**(to-tickets 之后、逐票执行之前):

- spec 每条需求/验收标准至少映射到一张 ticket;每张 ticket 能追溯回 spec 条目(孤儿票要么补 spec 要么砍掉)。
- blocker 图无环,存在可开工的 frontier ticket。
- 未解决问题为零,或逐条明确接受延期并记录。
- 每个高风险契约(schema/wire format/认证与权限面)写明验证方式。

**实施后**(全部票完成、总验证之前):

- 对 spec 逐条重放验收标准,用当次输出记录通过/失败。
- 发现遗漏→追加 ticket→再实现→再重放,直到 spec、tickets、实现、验证证据四者一致。
- 收敛完成才进入完成声明;重放记录写进报告。

## B. Bugfix

1. 最窄复现优先。
2. 根因未知→systematic-debugging 四阶段;已知→直接进 3。
3. 动手改文件前过 Task Delta Adapter 第 1-2 步快照;回归测试先 RED,修到 GREEN,只重构本次代码。
4. review 轴数按「有无正式 spec/ticket」定(与 routing.md 总表同一句): 无→Standards 单轴,有且非平凡→Standards+Spec 双轴。评审对象是 Task Delta Adapter 产出的本任务 patch;触及高风险边界**另加**安全/codex 镜头,不改变 Spec 轴的有无判定。
5. 定向测试+受影响面门禁命令;报告同 A.7。

## C. Review-only(只审不改)

只读取证→按有无 spec 选轴→结论并列报告→明确未验证范围。不修代码,问题列为建议。

## D. 新项目接手

1. 并行侦察: 结构 / 构建与测试命令 / 代码约定 / git 惯例。
2. 长期项目→建议 /init 生成 CLAUDE.md;满足创建门槛→按 [project-skill-template.md](project-skill-template.md) 生成项目 auto-skill。
3. 之后按 A/B 常规链;验证命令用侦察到的真实命令,不套其他项目的。

## E. 发版(仅用户明确要求时)

1. readiness(只读档): 读取 gstack review 的检查清单并对 delta 应用,**不调用完整 /review**——它自带 `git fetch`(改 remote-tracking refs)和 Fix-First(直接改文件)+持久化,超出只读授权。
2. 完整 /review: 仅当用户同时授权「允许修改」与必要的 git 更新时才调用。
3. 逐项确认授权范围(commit? push? 开 PR? 部署?)——不从「发版」二字推断全部授权。
4. 授权后才跑 ship 或 land-and-deploy;部署后按需 canary / document-release。

## F. 调研 spike

- **单问题**: MP research——后台 agent+一手来源+每条 claim 标来源,产出落盘(位置随仓库惯例);需要验手感→MP prototype(一次性代码,不混入主链)。
- **体系化调研**(技术选型/多体系对比/现状盘点——问题可分解为多个独立域时):
  1. 拆域,一域一个并行只读 agent(research 或 Explore,sonnet),各自输出结构化报告+来源,同一条消息批量派发;域间有依赖就串行,不硬并行。
  2. 综合留在主上下文,不外包: 合成结论文档,逐 claim 标出处,冲突处标注置信度。
  3. 综合后仍拿不准的取舍点,走 routing.md 的 Codex 协议拿第二意见。
  4. 结论落盘同上;后续按结论进入常规选路(如转 Playbook A)。

## G. 收尾 closeout(「收工/收个尾」)

1. 后台跑全量门禁拿新鲜证据(低档子代理执行命令、原样回传输出)。
2. 核对「已完成」声明 vs 实际改动与当次证据;对不上的如实记录。
3. 用户要求 closeout 时才更新项目进度文档(如 PROGRESS.md): 补齐里程碑与真实遗留(含欠着没跑的评审)。
4. /context-save 存会话上下文(与进度文档是两层,都要)。
5. 报告: git status 快照 + 验证结果 + 未提交声明 + 真实遗留清单。
6. 验证翻出的失败分三类处置: **本任务引入**→继续修复或标记 BLOCKED,不得声称完成;**原有失败**→记录 baseline 证据,不顺手修;**环境阻塞**→写明未验证范围与复现条件。「收尾不接新工作」指不开新需求,不等于放行自己引入的回归。

## Task Delta Adapter(所有修改路径通用)

默认不 commit 意味着任务改动只存在于工作树里,而 MP code-review 原版只接受「固定点→HEAD」的 diff——不经适配无法评审未提交改动。fast/focused/full 的每个修改类任务(或每张票)统一用本机制产出评审与报告用的任务专属 delta。**首选直接用 `scripts/task-delta.sh`**(begin/capture/render/cleanup;对仓库与 git 只读,仅写 0700 私有临时目录),手工执行时遵循同一规则:

1. 任务开始时记录 `git status --porcelain`;编辑任何文件**前**先把该文件此刻的副本存入私有临时目录(0700,仓库外)。收尾用 `git status --short` 交叉核对触及面——发现改了没快照的文件,如实披露归因失败并对该文件按全量内容评审,不得臆造任务专属 diff。
2. 仅当文件此刻真的不存在才记 ABSENT——前一票/前一任务创建的未跟踪文件是真实基线,不得再次记 ABSENT。
3. 敏感物料不进快照、不进 patch、不进子代理提示词: `.env*`、密钥/证书、数据库、构建产物、大型二进制与用户私有数据只记路径+必要哈希,确需评审就本地看并在报告说明(脚本会拒绝并在 patch 里留注记)。
4. 完成后逐文件 `git diff --no-index --no-ext-diff --no-textconv <快照副本> <现状>`,聚合为单一 patch;ABSENT 后新建的文件用 `/dev/null → 现状`,被删除的文件用 `快照 → /dev/null`;退出码 1 表示「有差异」,是正常结果不是错误(仅 >1 才是失败,脚本里勿被 `set -e` 误杀)。
5. 把 patch **显式交给** reviewer(单轴或双轴): 只借用 MP code-review 的双轴方法(Standards 轴+Spec 轴,上下文隔离,结论并列),不完整调用其 fixed-point 流程。
6. 报告里的「改动文件」以本 patch 为准——用户先前的脏改动被基线吸收,不进 patch、不被评审、不写进报告。任务收尾后 cleanup 快照目录。

## 验证分级(所有 playbook 通用)

- fast/focused: 与改动风险匹配的最小当次验证(定向测试/typecheck/构建其一至数项)。
- full/发版/高风险: 显式过 superpowers:verification-before-completion;需要全量矩阵时用 ecc verification-loop。
- 永远区分: 任务引入的失败 / 原有失败 / 环境阻塞;用当次输出说话。
- 项目有验证矩阵(auto-skill/文档)时用项目的;没有就按「触及面→定向命令→全门禁」自建最小矩阵并写进报告。

## auto 模式协议(无人值守公共权威：入口、授权信封、硬停、预算、出域与胶囊落点)

适用判断先行: 任务能在授权信封内闭环、且模糊度不超过「一句话需求」量级才可跑;wayfinder 级(路线不明的巨大任务)只产出假设清单+计划+风险声明后停。开局第一步: 按覆盖层固化**授权信封**(原始目标**脱敏摘录**——密钥/token/客户数据以 [REDACTED]+来源位置代替、修改范围、commit/push/发布/出域逐项 yes-no、禁止事项、执行预算)并写入目标契约。

**假设台账**(澄清链自答的产物,逐条):
```
A<n>. 假设: <一句话> | 依据: <仓库/文档/上下文证据> | 答者: <模型名> | 置信: 高/中/低 | 翻案点: <若假设错,从哪一步重做>
```
低置信假设优先安排在早期子任务验证;被当次证据推翻的假设立即改道并在台账标注。

**跨模型自答执行**: 主链起草完整问题清单(带最小必要上下文与主链候选答案)后一次派发,不逐问往返。答者必须不同于主链模型,按出域规则排序: ①默认同供应商跨档 Claude 子代理(Agent 的 model 参数选与主链不同的档,如主链 Opus→Fable、主链 Fable→Opus),只发送最小必要上下文;②跨供应商(codex xhigh 经 `codex-consult.sh @问题文件`)仅在数据出域已获授权(用户消息或项目约定明示)时使用;③密钥/.env/客户数据/私有文档永不进入咨询 prompt(同 Task Delta 敏感物料条款);④无出域授权且同供应商不可用时,不自动发送——台账记「缺少独立模型复核」继续。答者只读、不改文件、派发词声明 git 授权边界。答案是输入不是裁决——主链逐条采纳/驳回/降置信后才入台账。

**决策台账**(决策卡/产品取舍自决,逐条):
```
D<n>. 决策: <选了什么> | 备选: <放弃了什么> | 理由: <一句话> | 回滚: <怎么撤销>
```
选择原则: 决策卡取推荐项;无推荐项取最小可逆语义(影响面小、可撤销的一侧);两难且不可逆 → 硬停条件②。

**熔断与恢复胶囊**: 同一障碍三次实质尝试(换方法才算一次)无进展、或执行预算超限,即熔断。恢复胶囊 = **脱敏授权信封全文** + 已完成子任务清单 + 两份台账全文 + 卡点的最小复现 + 已排除的路径 + 下一步(敏感物料一律不入胶囊)。落点按授权水位(覆盖层规定): 只讨论/只读 review→仅留任务上下文不写文件;仅临时文件→系统私有临时目录;允许本地工件→`.scratch/<feature>/resume.md`。收尾报告引用。

**收尾报告模板**:
```
结果: <一句话> | 路径: <fast/focused/full> | 验证: <当次命令+关键输出摘引>
授权信封: <回显 + 未越界声明>
假设台账: A1..An(标注已验证/未验证)
决策台账: D1..Dn
副作用: <实际发生的文件/工件变更;信封内 git 操作逐条列出;未提交项明确声明>
未决: <留给用户的事项与建议,含被硬停跳过的动作>
```

**自动 compact**(auto 模式默认开启,不等用户触发): 触发条件=**上下文压力**(接近窗口限制/长任务临界);稳定边界——票据/子任务完成、验证通过、评审 CLEAN、台账更新后——只是允许压缩的安全时机: 有压力时推进到最近稳定边界先原子刷新恢复胶囊(脱敏授权信封、当前阶段与前沿、两份台账全文、验证证据、下一步)再压缩,无压力不压缩(胶囊仍按稳定边界刷新)。禁区=RED→GREEN 中途、评审或长命令运行中、结论尚未落盘。工具面无法主动 compact 时不得要求用户执行 /compact——继续推进或安全熔断交付胶囊。压缩后=重读胶囊,**先核对授权信封**,再与 git status、live 代码对账一致后继续。

**与既有纪律的关系**: Task Delta、验证分级、双轴 review、Codex 咨询协议全部照常;auto 只移除「中途向用户提问/确认」这一种交互,其余门禁一个不少。子代理派发提示词同样声明 auto 交互约束与 git 授权边界。
